### 1.2 事实表

```sql
fact_observation(                         -- 粒度：subject × 时刻 × 通道
  observation_id   BIGINT NOT NULL,       -- 代理列：唯一索引，仅供 provenance/调试引用
  subject_id       VARCHAR NOT NULL,
  observed_at      TIMESTAMP NOT NULL,
  date_key         INTEGER NOT NULL,
  channel          VARCHAR NOT NULL,      -- 10 个日粒度通道 + heart_rate（见 §2）
  value            DOUBLE NOT NULL,
  source_id        VARCHAR NOT NULL,
  recorded_at      TIMESTAMP NOT NULL,
  PRIMARY KEY (subject_id, observed_at, channel)
)
-- 为什么用**业务自然键**作主键：
-- 观测没有天然身份——同一主体、同一通道、同一时刻只应有一条读数。
-- 用自然键才能让"重复插入"被数据库**拒绝**：`obs_daily` 用
-- `sum(value) FILTER (WHERE channel = ...)` 汇总当日观测，
-- 一条重复观测会让当日数值**翻倍且无任何报错**。

fact_event(                               -- 粒度：事件
  event_id         BIGINT PRIMARY KEY,    -- ⚠️ 代理键，见下方说明
  subject_id       VARCHAR NOT NULL,
  occurred_at      TIMESTAMP NOT NULL,
  date_key         INTEGER NOT NULL,
  event_type       VARCHAR NOT NULL,      -- transaction | note | llm_turn | workout
  amount           DOUBLE,                -- 单位随类型变：transaction=金额 ｜ workout=分钟
  category         VARCHAR,               -- transaction=消费类别 ｜ workout=运动种类
  text             VARCHAR,               -- note / llm_turn 用
  source_id        VARCHAR NOT NULL,
  recorded_at      TIMESTAMP NOT NULL
)
-- ⚠️ `fact_event` **刻意不加自然键唯一约束**：
-- 同一分钟的两笔消费是完全正常的，而 `occurred_at` 只精确到分钟；
-- 事件的真身份必须由上游提供（如 `source_event_id`），当前数据源没有，如实留空。
--
-- ⚠️ **`amount` / `category` 的单位随 `event_type` 变化**（"事件表"的固有形态：
-- 类型决定哪些列有意义，其余列为 NULL）：
--   transaction → amount = 金额（元），category = 消费类别
--   workout     → amount = **运动时长（分钟）**，category = 运动种类
--   note / llm_turn → 两者均为 NULL，内容在 text
-- 当前只有 transaction 路径被指标消费；workout 的时长没有指标在用。
-- 若将来要加"周运动时长"指标，需先在 `veriself/semantic_models/event.yml` 里聚成逻辑列。

fact_metric_value(                        -- 粒度：metric × subject × date（物化结果，双时间轴）
  metric_id        VARCHAR NOT NULL,
  subject_id       VARCHAR NOT NULL,
  date_key         INTEGER NOT NULL,      -- 见下方「date_key 的语义（冻结）」
  value            DOUBLE NOT NULL,
  metric_version   INTEGER NOT NULL,
  contract_hash    VARCHAR NOT NULL,
  computed_at      TIMESTAMP NOT NULL,
  valid_from       TIMESTAMP NOT NULL,
  valid_to         TIMESTAMP,             -- NULL = 有效
  PRIMARY KEY (metric_id, subject_id, date_key, valid_from)
)

-- `date_key` 的语义（冻结）：**桶内最后一个有数据的真实日期**（yyyymmdd 整数），
-- 不是桶的起始日，也不是桶的名义结束日。
--   grain=day   ：该日期本身
--   grain=week  ：该 ISO 周（周一起算，date_trunc('week')）内最后一个有数据的日期，
--                 通常是周日；数据在周中截止时会早于周日
--   grain=month ：该月最后一个有数据的日期
--   grain=quarter：同理
-- **保证 `date_key` 恒为真实存在的日期**，因此可以与 `dim_date` 内连接。
--
-- 桶的起止区间**不存储**，由 `date_key + dim_metric.grain` 派生：
--   week : period_start = date_trunc('week', date_key)，period_end = date_key
--   month: period_start = date_trunc('month', date_key)，period_end = last_day(date_key)
--   day  : period_start = period_end = date_key
--
-- ⚠️ **不要把 `date_key` 当成桶标识，也不要按它给"跨桶"的周/月归月**：
--    例如 period 2024-01-29..2024-02-04 的周，date_key = 20240204（属 2 月），
--    但它的数据有 3 天落在 1 月。归到哪个月是**聚合口径决策**（按结束日？按占比？），
--    不是存储问题——加列也无法替你决定。

fact_subject_day(                         -- 粒度：subject × date（日情境事实，不是维度）
  subject_id       VARCHAR NOT NULL,
  date_key         INTEGER NOT NULL,      -- yyyymmdd
  is_travel        BOOLEAN NOT NULL,
  is_illness       BOOLEAN NOT NULL,
  location_type    VARCHAR NOT NULL,      -- 'home' | 'office' | 'other'
  PRIMARY KEY (subject_id, date_key)
)
-- 与 fact_metric_value 连接必须同时用 subject_id 和 date_key。
-- 只按 date_key 连接会在多主体时把同一天的情境乘到每个主体上。
-- 查询名是 context.is_travel / context.is_illness / context.location_type。

fact_audit_log(
  audit_id         BIGINT PRIMARY KEY,
  queried_at       TIMESTAMP NOT NULL,
  actor_role       VARCHAR NOT NULL,      -- owner | partner | researcher
  request_json     VARCHAR NOT NULL,
  compiled_sql     VARCHAR,
  metric_versions  VARCHAR,
  contract_hashes  VARCHAR,
  rls_applied      VARCHAR,
  checks_passed    VARCHAR,
  outcome          VARCHAR NOT NULL       -- ok | rejected:<rule>
)
```

## 2. 指标契约 schema（冻结）

目录：`veriself/metrics/*.yml`（一个文件一个指标）
加载器：`veriself/semantic/contract.py`（Pydantic v2 模型）

```yaml
metric_id: subject.sleep_debt_7d     # 必填，唯一，点分小写（格式校验见下方「metric_id 格式」）
version: 1                            # 必填，整数
status: active                        # draft | active | deprecated
owner: jiayezi                       # 必填
display_name: 近7日睡眠债
synonyms: [睡眠债, 这周欠了多少觉, sleep debt]
definition: 过去7日(含当日)每日睡眠缺口之和；缺口 = 睡眠需求 - 实际睡眠
unit: hour                            # hour|count|score|currency|ratio|minute
direction: lower_better               # higher_better | lower_better | neutral
agg: sum                              # **跨时间粒度上卷方式**：sum|mean|min|max|last
grain: day                            # day | week | month | quarter
entity: subject
allowed_dimensions: [date.weekday, date.month]   # 白名单，越界即拒绝
allowed_filters: [date.between, date.last_n_days]  # 白名单
rls_policy: owner_only                # owner_only | aggregate_min5 | no_pii
formula_sql: |                        # 必填，只能引用 lineage.sources 里声明的对象
  sum(greatest(s.sleep_need_h - o.sleep_hours, 0))
bucket:                              # 可选（仅 grain != day）：桶内聚合声明
  agg: sum                           # 桶内聚合：sum|mean|min|max|last（last=取桶内最后一天值）
lineage:
  sources: [fact_observation.sleep_hours, dim_subject.sleep_need_h]
  upstream_metrics: []                # 允许引用上游 metric_id
deprecation:                          # 可选；空块（replaced_by=null）可整体省略
  replaced_by: null
  sunset_at: null
```

**`metric_id` 格式（冻结）**：必须是"点分小写"——`^[a-z][a-z0-9_]*(?:\.[a-z][a-z0-9_]*)*$`。
即段首小写字母，段内只含小写字母/数字/**下划线**，用点分隔（如 `subject.sleep_debt_7d`、
`subject.sleep_need_deviation_daily`）。大写、连字符、空格、空段、前导数字、
段首下划线、前后多余点一律在加载期拒绝（`ContractError`）。理由：`metric_id` 会被字符串
插值进物化 SQL 与查询 SQL，格式约束是注入面/解析歧义的第一道闸门。校验实现于
`semantic/contract.py` 的 `_check_metric_id`（`metric_contract_from_mapping` 内，
YAML 加载与程序化构造同一条路径）。

**`allowed_dimensions` / `allowed_filters` 白名单（冻结）**：
- 维度允许：`date.weekday`、`date.day_of_week`、`date.month`、`date.quarter`、
  `context.is_travel`、`context.is_illness`、`context.location_type`
  - `date.weekday` 是**星期名**（`"Monday"`…），按它排序得到的是**字母序**（Friday 排在 Monday 前）；
    做"周内趋势"**必须**用 `date.day_of_week`（1=周一 … 7=周日，数字型）。
    两者同时保留是刻意的：名字给人看，数字给排序用。
  - ⚠️ **按维度分组时，结果里仍会带上 `date.day`**（编译器把生效粒度的日期列作为默认输出列）。
    因此"周内分布"类问题需要调用方自行再聚合；语义层当前不提供"只按维度聚合、丢掉日期列"的模式。
    这是已知行为，改动它需要先决定该模式的取舍（会与"每个数都可追溯到具体日期"冲突）。
  - `context.*` 来自 `fact_subject_day`。编译器按 `(subject_id, date_key)` 与
    `fact_metric_value` 内连接。两个键必须同时出现。
- 过滤器允许：`date.between`、`date.last_n_days`、`date.month`、
  `context.is_travel`、`context.is_illness`、`context.location_type`

**语义说明（两个易错点）**：
- **物理列 vs 逻辑列**：`fact_observation` 是"通道-值"窄表（只有 `channel` + `value`），`fact_event` 只有 `amount`/`category`。因此 `lineage.sources` 与 `formula_sql` 里写的是**逻辑列**（`fact_observation.sleep_hours`、`fact_event.spending`、`fact_event.note_count`），**定义在 `veriself/semantic_models/*.yml`**（observation：通道 + 日聚合方式；event：自由 expr；subject：维度列），由 `materializer` 据此生成 `obs_daily`/`evt_daily`/`subject_current` 视图。`fact_event.amount` 不能直接引用。
  ⚠️ **加载期做真实列存在性校验**：公式与 `lineage.sources` 里的列名 typo
  （如 `fact_observation.sleep_hour`）在 `load_contracts` 即拒绝，不会拖到物化期 Binder Error。
- **`*_7d` 类滚动指标的 `agg`**：`grain=day` 但其值本身已是滚动量，day→month 上卷得到的是"滚动值的均值"，**不等于**月度均值。这是已知的语义近似，展示时应以日粒度为默认视图。

**`formula_sql` 的两种引用形式（冻结）**：
- 引用原始数据源：直接写 `表.列`，如 `o.sleep_hours`，该列必须出现在 `lineage.sources`。
- 引用上游指标（派生指标专用）：写 `metric('subject.sleep_duration_daily')`，该 metric_id 必须出现在 `lineage.upstream_metrics`。

**`formula_sql` 书写约定（冻结，`materializer` 依赖这些约定，违反会在物化期失败；
列名 typo 除外——加载期即拒绝，见上方"物理列 vs 逻辑列"）**：
1. **公式里一律写物理表名**：`fact_observation.<通道>`、`fact_event.<逻辑列>`、`dim_subject.<列>`。
   物化器会把它们重写成查询别名 `o.` / `e.` / `s.`（**别名形式 `o.x` 也接受**，但 YAML 里建议统一写物理表名，便于阅读理解血缘）。
2. **可用列**：
   - `fact_observation.*`（当日观测，日粒度已聚合）：`sleep_hours`、`sleep_start_hour`、`resting_hr`、`hrv`、`deep_sleep_hours`、`steps`、`exercise_minutes`、`focus_score`、`screen_minutes`、`mood_score`、`date_key`
   - `fact_event.*`（当日事件）：`spending`、`note_count`、`llm_turn_count`、`workout_count`、`discretionary_spending`、`date_key`
   - `dim_subject.*`（当前版本）：`name`、`birth_date`、`sleep_need_h`、`base_weight_kg`、`timezone`
3. **裸 `date_key` 指"正在计算的那一天"，且唯一无歧义**。窗口函数用它排序：
   `sum(...) OVER (ORDER BY date_key ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)`
   ⚠️ **不要**写 `fact_observation.date_key` 或 `o.date_key` 作为窗口排序键：来源表的日期列在物化时已改名为 `obs_date_key`/`evt_date_key`（正是为了避免与骨架 `date_key` 歧义），显式限定反而绑不上。
   **`date_key` 也不能作为普通列出现在 `formula_sql` 里参与算术**，只能用于 `OVER (ORDER BY ...)` 或 `CASE WHEN` 条件。
4. **窗口函数只用于表达跨时间逻辑**；含 `OVER` 的公式在物化时**原样落库、不再聚合**（否则滚动和会被二次平均）。不含 `OVER` 的公式按其 `grain` 桶取 `arg_max`。
5. **公式是"日粒度标量表达式"，不能写普通聚合**（例如 `avg(o.sleep_hours)` 会报 GROUP BY 错误）。跨时间聚合只能用 `OVER(...)` 表达。
6. 每个 `formula_sql` 必须至少引用一个来源表或一个上游指标——否则无法确定日期骨架，物化会报错。
7. **非日粒度（`grain` = week/month/quarter）有两种合法形态**：
   - **声明式 `bucket`（推荐）**：`bucket: {agg: <sum|mean|min|max|last>}`
     声明桶内聚合方式，物化器自动完成桶聚合并取桶内最后一个有数据的日期为 `date_key`。
     此时 `formula_sql` 必须是**日粒度标量表达式**（不能写窗口函数/普通聚合）。
     `last` = 取桶内最后一天的值（`arg_max(value, date_key)`）。
   - **手写窗口 + CASE（旧形态，向后兼容）**：公式自己完成桶内聚合并标记代表行，
     推荐写法（已被测试覆盖）：
     ```sql
     CASE WHEN date_key = max(date_key) OVER (PARTITION BY date_trunc('week', strptime(CAST(date_key AS VARCHAR), '%Y%m%d')))
          THEN avg(fact_observation.sleep_hours) OVER (PARTITION BY date_trunc('week', strptime(CAST(date_key AS VARCHAR), '%Y%m%d')))
     END
     ```
     语义：窗口函数对桶内所有天算出同一个桶值；`CASE` 保证只有代表行（桶内 date_key 最大者）非空。
     物化器随后按桶只保留一行，`date_key` 取**桶内最后一个有数据的真实日期**
     （精确定义见 §1「`date_key` 的语义（冻结）」，此处不重复）。
   - ⚠️ **两者互斥**：声明 `bucket` 后公式里再写 `OVER(...)` 会在加载期被拒
     （两套桶机制会产生二义性）。

**校验规则（加载时必须强制）**：
1. `metric_id` 唯一；重复即启动失败。
2. `formula_sql` 中出现的每个 `表.列` 必须能在 `lineage.sources` 里找到（前缀匹配 `表名.`）；每个 `metric('x')` 必须能在 `lineage.upstream_metrics` 里找到。
3. `status=deprecated` 时 `deprecation.replaced_by` 必填。
4. `grain`、`direction`、`unit`、`agg` 必须 ∈ 各自枚举。
5. `upstream_metrics` 引用的 metric_id 必须存在，且**禁止环**（拓扑排序可检出）。

**跨粒度上卷语义（冻结）**：`formula_sql` 产出的是 `grain` 声明的粒度的值；当查询请求更粗的粒度（如 day → month）时，编译器必须按 `agg` 聚合：
- `sum` → `SUM(value)`（如睡眠债、支出、次数）
- `mean` → `AVG(value)`（如专注度得分、睡眠时长）
- `min` / `max` / `last` → `MIN` / `MAX` / `arg_max(value, date)`
**当 `grain` 与请求粒度相同时，禁止聚合**（直接取原始值）。

## 4. 审计头（冻结）——每次响应必须携带

```python
{
  "data": [ {...} ],
  "audit": {
    "metric_versions": {"subject.sleep_debt_7d": 1},
    "contract_hashes": {"subject.sleep_debt_7d": "sha256:..."},
    "compiled_sql": "SELECT ...",
    "rls_applied": ["owner_only"],
    "enforced_checks": ["registered", "dimensions", "grain", "ast_join_path", "rls"],
    "as_of_definition": "2026-10-01",
    "queried_at": "2026-10-01T16:40:00+08:00"
  }
}
```

**`enforced_checks` 的语义（冻结）：记录本次查询**实际执行过**的校验。**

- 它**不是**把 `config.ENFORCED_CHECKS` 抄一遍——那样这一栏就只是配置回显，
  证明不了任何事（删掉某条校验，审计头依然会声称五条全部通过）。
- 实现上由 `compile_query` 在每条校验**成功返回后**追加名称；没执行到的不会出现。
- 输出顺序为契约声明的规范顺序（`ast_join_path` 在 `rls` 之前）。
  ⚠️ **实际执行顺序是 `rls → ast_join_path`**：必须先算出 RLS 改写计划，
  才能对**最终**（含 RLS）的 SQL 做结构校验。对外只暴露规范顺序，避免读者以为契约写错。
- 校验失败时不会产出审计头（走 `outcome=rejected:<rule>` 记录），因此
  "这一栏短了"只可能意味着代码被改动，而不是某次查询碰巧跳过。

`contract_hash` 算法（冻结）：`"sha256:" + sha256(规范化 JSON 文本).hexdigest()[:16]`。
**规范化的实现以代码为唯一权威**：`veriself/contract_hash.py`（`sort_keys=True`、`ensure_ascii=False`、**紧凑分隔符 `separators=(",", ":")`**）。
`semantic` / `warehouse` / `materializer` 三方必须 import 同一函数，不得各自实现；固定样例
`{"metric_id":"subject.demo","version":1,"unit":"hour","agg":"sum","grain":"day"}` → `sha256:015c2525e5106928` 在三处测试中都必须成立。

## 5. 五条强制校验（冻结，拒绝原因字符串固定）

| 顺序 | 校验名 | 拒绝时 `reason` 前缀 |
| --- | --- | --- |
| 1 | `registered` | `unknown_metric:` / `deprecated_metric:` |
| 2 | `dimensions` | `dimension_not_allowed:` / `filter_not_allowed:` |
| 3 | `grain` | `grain_not_compatible:` |
| 4 | `ast_join_path` | `ast_violation:` |
| 5 | `rls` | 不拒绝，**改写 SQL** 并记录 `rls_applied` |

**校验顺序（冻结）**：上表是**规范顺序**，也是审计头 `enforced_checks` 的输出顺序。
⚠️ **实际执行顺序在第 4/5 条上与规范顺序不同**（有意为之）：

```
实际执行：registered → dimensions → grain → rls → ast_join_path
规范顺序：registered → dimensions → grain → ast_join_path → rls
```

原因：`rls` 只依赖契约与角色、不依赖 SQL，先算出改写计划后 SQL 只需构造一次，
`ast_join_path` 直接对**最终**（含 RLS）的表达式树校验——避免先构造一份"未注入 RLS"的
SQL 校验后丢弃，再把渲染字符串交给 AST 校验（二次解析）。

**副作用（须知晓）**：一次请求**同时**触发多条拒绝时，报出的 `rule` 取决于执行顺序——
例如"维度不在白名单"且"角色无权"同时成立时，现在是 `dimensions` 而不是 `rls`。
单条违规的报错不受影响。

额外预检：编译后执行 `EXPLAIN`，估算行数超 `limit_hint`（默认 1e7）则拒绝，reason 前缀 `scan_too_large:`。

## 7. `semantic` 模块公开 API（冻结，`interfaces` 按此调用）

```python
# veriself/semantic/__init__.py

from veriself.semantic.contract import MetricContract, load_contracts
from veriself.semantic.query import QueryRequest, CompiledQuery, QueryResult
from veriself.semantic.compiler import compile_query, execute_query
from veriself.semantic.catalog import list_metrics, describe_metric

def load_contracts(metrics_dir: Path | None = None) -> dict[str, MetricContract]:
    """加载并校验 metrics/*.yml。重复 metric_id / 环 / 非法枚举 → 抛 ContractError。"""

class QueryRequest(BaseModel):
    metrics: list[str]                       # 必填非空
    dimensions: list[str] = []
    filters: dict[str, object] = {}
    grain: str | None = None
    order_by: list[dict[str, str]] = []
    limit: int = 1000                        # 上限 config.DEFAULT_LIMIT

    @classmethod
    def from_json(cls, raw: str | dict) -> "QueryRequest":
        """解析并做注入面检查：任一字符串值含 SQL 关键字/注释/分号 → 抛 QueryError。"""

class CompiledQuery(BaseModel):
    request: QueryRequest
    sql: str                                 # 已注入 RLS 的最终 SQL
    params: list[object] = []
    metric_versions: dict[str, int]
    contract_hashes: dict[str, str]
    rls_applied: list[str]
    enforced_checks: list[str]               # **实际执行过**的校验（按规范顺序），见 §4 说明

class QueryResult(BaseModel):
    data: list[dict]                         # 行数据
    audit: dict                              # 结构见本文件第 4 节

def compile_query(
    req: QueryRequest,
    contracts: dict[str, MetricContract],
    role: Role = Role.OWNER,
) -> CompiledQuery:
    """执行五条强制校验并生成 SQL。被拒绝时抛 EnforcementError(rule, detail)。"""

def execute_query(
    compiled: CompiledQuery,
    role: Role = Role.OWNER,
    conn=None,                               # duckdb 连接；None 时自建
    audit: bool = True,                      # True 时写 fact_audit_log
) -> QueryResult:
    """执行 + EXPLAIN 预检 + 写审计日志 + 组装 audit 头。"""

def list_metrics(contracts: dict[str, MetricContract]) -> list[dict]:
    """返回目录摘要：[{metric_id, display_name, unit, direction, grain, status, version}]"""

def describe_metric(contracts: dict[str, MetricContract], metric_id: str) -> dict:
    """完整契约 + contract_hash + 血缘 + 可用维度/过滤器。未知 metric_id 抛 EnforcementError。"""
```

**跨模块铁律**：
1. `interfaces` 层**不得**自行拼 SQL、不得直接 import `duckdb` 执行业务查询；一律走 `compile_query` + `execute_query`。
2. `semantic` 层**不得**读 `metrics/*.yml` 原始文本以外的文件系统内容，不得依赖 `synth` 或 `interfaces`。
3. `warehouse` 层只负责 DDL 与装载，**不得**实现校验逻辑。
4. 任何模块不得修改 `veriself/config.py`。

### 7.1 其余模块签名（冻结，`interfaces` 据此调用）

```python
# veriself/warehouse/loader.py
def ensure_schema(conn) -> None
def upsert_dim_metric(conn, contracts) -> int          # contracts: dict[metric_id, MetricContract]

# veriself/synth/__init__.py

```

### 7.2 `limit` 语义（冻结）

`limit` 超过 `config.DEFAULT_LIMIT` 时由 **`semantic.QueryRequest` 直接拒绝**（`config.QueryError`），
**不做静默截断**——静默截断会让调用方拿到"看起来完整但不完整"的数据，正是本项目要消灭的失败模式。

### 7.3 请求对象封闭性（冻结）

`QueryRequest` 使用 `extra="forbid"`：携带任何未声明字段（如 `sql`）一律被拒。
MCP 工具的入参 schema 由 `interfaces` 显式收紧为 `additionalProperties: false`——
SDK 默认不封闭，不收紧则"接口不接受 SQL"这句话在协议层不成立。

## 8. `materializer` 模块公开 API（`interfaces` 的 `veriself init` 按此调用）

**存在理由**：`semantic` 读 `fact_metric_value`，但总得有人把 18 个指标算进去。这个模块按契约的 `lineage` 拓扑分层计算并物化。

> ⚠️ **唯一权威入口是 `materialize_all`**。`warehouse.loader.materialize_metric` 是更底层的原语，它的关闭语义只覆盖"本批次 `(subject_id, date_key)`"，而 `materialize_all` 按**键**做合并。**同一条指标不要混用两条写入路径**。

```python
# veriself/materializer/__init__.py

def materialize_all(
    conn,                                      # duckdb 连接
    contracts: dict[str, MetricContract],
    *,
    batch_ts=None,                             # 批次时间戳（测试用）；默认当前 UTC
    models=None,                               # 语义模型集（semantic_models/*.yml）；None 时自动加载
) -> dict[str, dict[str, int]]:
    """按 lineage 拓扑顺序计算全部指标，并以**合并**方式写入 fact_metric_value。

    分层规则（冻结）：
      第 0 层：lineage.sources 只引用 fact_observation / fact_event / dim_* 的指标
      第 n 层：引用第 n-1 层及更早的 metric('...') 的指标
    同层内按 metric_id 排序，保证确定性。

    合并语义（冻结）：
      值与口径都没变 → 跳过（不关旧行、不插新行）
      值或口径变化   → 关闭旧行 + 插入新行
      键不再产出     → 关闭且不插入（防僵尸有效行）
    因此**重算幂等**：无变化时零写入。

    返回：{metric_id: {"live", "inserted", "closed_changed", "closed_vanished", "unchanged"}}
    失败：契约环或引用不存在的上游 → 抛 config.ContractError
    """
```

**版本作用域（冻结）**：物化只作用于 `metric_version = <契约版本>` 的行，
**不会**关闭其他版本。因此同一指标可同时存在多个有效版本，**读取时必须带版本过滤**：

```sql
WHERE valid_to IS NULL AND metric_version = <契约当前版本>
```

`semantic` 已按此实现；裸查询（不带版本）会同时读到多个版本的行，这是明确记录的陷阱。

**计算语义（冻结）**：
- 第 0 层指标的 `formula_sql` 在 `fact_observation` / `fact_event` 的**日粒度**上求值：按 `date_key` 分组，用契约 `agg` 聚合当日原始观测。
- 派生指标的 `formula_sql` 中，`metric('X')` 展开为对 `fact_metric_value` 的子查询（`metric_id='X' AND valid_to IS NULL AND metric_version=<当前版本>`）。
- 派生指标**跨时间聚合**使用**窗口函数**，窗口由 `formula_sql` 自己声明（例如 `sum(...) OVER (ORDER BY date_key ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)`），**不得**依赖编译器的跨粒度上卷。
- 写入的 `date_key` 范围取 `fact_observation`/`fact_event` 与**上游指标**日期范围的并集
  （纯派生指标的骨架来自上游，不能只看原始表）。
- 硬性要求：**禁止对 NaN/Inf 写入**；无数据的日期不写行（而不是写 0）。
- **值等价判定带浮点容差**（`materializer.VALUE_REL_TOL = 1e-9` + `VALUE_ABS_FLOOR`）：
  DOUBLE 求和/平均的顺序不稳定，末位会漂移，精确比较会让每次重算都留下噪声历史。
