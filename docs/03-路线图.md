# 路线图（v0.1 → v1.0）

> v0.1 的验收标准是"**受约束的指标执行层可以端到端跑通，且红队攻不破**"，不是功能多。
> 因此 v0.1 刻意砍掉了前端、多主体、增量与真实连接器。

## v0.1（当前版本）

- 合成个人纵向数据（3 年、1004 天、106,424 条观测、5,882 条事件）
- DuckDB：`dim_date` / `dim_subject`(SCD2) / `dim_source` / `dim_metric`
  + `fact_observation` / `fact_event` / `fact_subject_day` / `fact_metric_value`(双时间轴) / `fact_audit_log`
- 18 个指标契约（YAML，含版本、单位、方向、上卷方式、血缘、RLS 策略）
- 语义层：契约加载校验（含列存在性）→ sqlglot 编译 → **五条强制校验** → RLS 改写 → 审计头
- 物化器：按 lineage 拓扑分层计算，双时间轴留痕（重算幂等、合并语义）
- 来源语义模型：`semantic_models/*.yml`（逻辑列定义：通道→日粒度列、事件逻辑列、维度列）
- CLI（`veriself init/synth/query/metrics/audit/reject/demo/mcp`）+ MCP server（4 个工具，stdio）
- 测试：全量 + 端到端红队验收（22 项走真实链路）

## 仓库结构（已定）

**单仓库**（monorepo），不拆成"数据端 / 后端 / 前端"三个仓库。应用层代码放 `apps/`：

```
veriself/
├── veriself/              # 引擎包（含 metrics/ 与 semantic_models/）
├── tests/  docs/
└── apps/
    ├── api/                  # 录入 + 读 API（import veriself）
    └── web/                  # 前端
```

理由：

- **契约就是接口**：`metrics/*.yml` / `semantic_models/*.yml` 是引擎与应用之间唯一的契约。
  拆仓就得跨仓库发布与版本化这份契约，恰好削弱本项目"契约决定一切"的卖点。
- **一次功能横跨多层**：新增一个观测（如血压）要同时改语义模型、指标契约、ETL、后端校验、
  前端表单——单仓库里这是一次原子 PR、一次 CI。
- **单人开发**：polyrepo 的收益（团队自治、独立发布节奏）用不上，只剩锁步发版的成本。
- **`mono → poly` 便宜，`poly → mono` 贵**（`git filter-repo` 能带走历史，合并历史很痛）：
  所以先单仓库，将来真需要再抽出去。
- **单仓库 ≠ 单部署单元**：可以一个仓库、多个可部署产物，CI 按路径过滤。

**只在需要硬墙时才拆。** 唯一可能触发的是**隐私/许可证**：引擎是 Apache-2.0 开源，
而应用会保存个人健康数据。若那时要隔离，拆成 2 个（`veriself`＝引擎 + 读 API ｜
`veriself-app`＝录入后端 + OLTP + ETL + 前端），**不要把 API 与 Web 拆开**——
它们共享同一个 REST 契约、同批改动、服务同一批用户。

**应用层的三条约束**（落实时不得违反）：

1. **录入校验由契约派生**：可录入的通道、单位、取值范围从 `semantic_models/*.yml` 取，
   让"前端表单 / 后端校验 / 数仓通道"同一个来源——否则"不可能算错"会在**入口处**漏掉。
2. **读路径仍走语义层**：后端不得手写 SQL，一律 `compile_query` / `execute_query`。
3. **OLTP 与数仓分离**：业务库（可变更、点查）≠ 数仓（追加 + SCD2、聚合）。
   用户录入落 OLTP，`fact_observation` 仍由 ETL 派生（与 `synth` 现在的角色相同）。

## v0.2（建议下一阶段，约 4-6 周业余时间）

按"对传播力贡献"排序：

1. **多主体支持**（最高优先级）。当前只生成 1 个主体 `S001`，导致 `aggregate_min5` 策略对
   `partner` / `researcher` 角色恒返回空——隐私语义是对的，但演示观感像 bug，也无法展示
   "同一指标、不同角色、不同可见范围"这个核心卖点。
   改动：`config` 加主体数量 → `synth` 生成 6-8 个主体（各自的睡眠需求与行为差异）→
   `dim_subject` 多行 → partner 查询可返回真实聚合值。
2. **日情境事实 `fact_subject_day`**（已完成）。`dim_context` 与 `fact_memory_assertion` 已删除。
   情境是每人每天一行，主键 `(subject_id, date_key)`。查询名是 `context.is_travel` /
   `context.is_illness` / `context.location_type`，18 个当前指标已放开。
   多主体时按主体加行。连接必须同时用 `subject_id` 和 `date_key`，不要恢复没有主体键的状态组合维。
3. **`as-of` 查询接口化**。数据层已支持（`metric_version` + `contract_hash` + 双时间轴），
   但还没有对外入口。目标：`veriself query --as-of 2026-03-01` 能回答
   *"按当时的口径，那天算出来是多少"*，并给出与当前口径的 diff。
   这是竞品普遍缺失、且最能体现数据工程功力的能力。
4. **口径版本 diff 报告**。两个版本的口径差异 + 影响到的指标/页面清单（列级血缘已有数据基础）。
5. **领域描述符：把物理模型从引擎代码里抽出来**（`domains/*.yml`）。
   这是 [v1.0 第 15 项「第二个 adapter」](#v10半年后) 的前置条件——不做这一步，
   "第二个 adapter"只能靠复制引擎代码实现，那是 fork，不是 adapter。

   **现状**：引擎逻辑本身与领域无关（拓扑分层只依赖 `lineage`；五条校验、sqlglot AST、
   RLS 改写、双时间轴都不含领域词汇），但物理模型硬接在**两个领域专属文件**上：

   | 位置 | 硬编码内容 |
   | --- | --- |
   | `semantic_models/*.yml` | 通道名/事件逻辑列/维度列（睡眠/健康/消费词汇）——已声明化，但本身就是一个领域 |
   | `obs_daily` 按 **day** 聚合 | 主时间粒度写死为"天" |
   | `spine` = `(date_key, subject_id)` | 主体 × 日期是唯一骨架 |
   | `subject_asof` 视图 | `dim_subject` 按业务日落入 `[valid_from, valid_to)`；查询期维度仍用 `is_current` |
   | `semantic.lineage.JOIN_PATHS` / `DIMENSION_TABLES` | 写死的 JOIN 组合与维表名单 |
   | `semantic.catalog.COLUMN_ALIASES` / `TABLE_COLUMNS` / `FILTER_KINDS` | 维度名 → 物理列名、各表列白名单、过滤器形态 |
   | `semantic.compiler` | 无条件 `INNER JOIN dim_date AS d` 与固定表别名 |

   **目标**：新增 `domains/person.yml`（首个 adapter），内容形如——`subject_dimension` /
   `subject_key` / `time_dimension` / `time_key` / `grain`、各来源表的 `shape`
   （`channel_value` 窄表 / 事件派生列 / 维度）、`channels` 及各自聚合、`dimensions`、
   `joins`。`materializer` 与 `semantic` 都从它读。

   **收益**：换领域 = **换一个 YAML + 写一批指标契约**，引擎一行不动、现有测试不用改。

   **顺带修掉的不一致**：项目主张"契约决定一切"，指标契约已是声明式的，
   但"哪些表有哪些列、谁能 JOIN 谁、主体键叫什么"同样属于契约，却散在 Python 常量里。
   抽出这一层不是增加复杂度，而是让两处用同一种设计语言。

## v0.3（前端，约 4 周）

6. **Vue3 + ECharts 多角色界面**：指标卡（含口径与哈希）、角色切换（owner/partner/researcher）、
   拒绝原因可视化、审计日志时间线、血缘图。菜单权限挂角色。
   注意：前端只消费 `semantic` 的 API，不得绕过语义层。

7. **放开 `date.*` 维度白名单**（**能力扩充，非缺陷**；前端要用到时提前做）。
   现状：catalog 暴露了 10 个 `date.*` 语义名，但 18 个契约的白名单**只允许 4 个**
   （`weekday` / `day_of_week` / `month` / `quarter`）。因此下面这些**表达不出来**：

   | 维度 | 缺失的后果 |
   | --- | --- |
   | `date.year` | 无法一次查出"2024 / 2025 / 2026 各一行"的**年度趋势**，只能分年查或调用方自己聚合 |
   | `date.is_weekend` / `date.is_holiday` | **"周末 vs 工作日"**这类最常见的行为差异分析无法表达 |
   | `date.week` | 无法按自然周分组（现有 `date.weekday` 只是星期名/序号） |

   `synth` 里**植入了周末效应**（`latent_daily` 用 `is_weekend` 推导 `location_type`），
   数据有信号，查询层却表达不出来。

   改动：给 18 个契约的 `allowed_dimensions` 加维度 + 同步测试里冻结的 `DIMENSION_VOCABULARY`
   + 更新 `docs/01`。**catalog 的映射已存在**（无需改 `catalog.py`）。
   代价：全部 `contract_hash` 变化——这对本项目是**正常**的（白名单属于口径的一部分）。
   注：`FILTER_KINDS` 也只有 `between` / `last_n_days`，若要按等值过滤 `is_weekend` 等，
   需一并扩展。

8. **滚动窗口的"不完整窗口"**（观察项，**建议先只调研、不改**）。
   4 个 `*_7d` 指标的数据集**开头 7 行**由不完整窗口算出（第 1 行实际是"单日值"），
   却与完整窗口的行完全无法区分；多主体之后**每个主体的开头 7 行**都会如此。
   它**不是缺陷**（"过去 7 天的睡眠债"在第 1 天评估，返回那 1 天的值站得住），
   而是容易与完整窗口混淆。
   若要做，两个方向：① 不完整窗口返回 `NULL`（明确但改变数值），
   ② 响应里标注"本值为 N 日滚动统计量"（不改变数值，属接口变更）。
   **注意：不要采用"编译器拒绝跨粒度上卷"那条路**——上卷发生在调用方，编译器原理上拦不到，
   且会拦掉合法功能。

## v0.4（工程化）

9. **增量与 watermark**：当前是全量重建（3 年数据 1.4 秒，够用）。
   引入增量后要处理"迟到数据"与"重算范围"，这才是有难度的部分。
10. **真实连接器**：从合成数据过渡到真实来源（Apple Health 导出、银行 CSV、Markdown 笔记目录）。
    这是让项目"有用"的关键一步。
11. **FastAPI HTTP 层**：MCP 之外提供 REST（同一语义内核，两种传输）。
12. **Docker Compose**：需在有 Docker 的环境验证后再写进 README。
13. **录入应用（写路径）**：Web 录入 → 业务库(OLTP) → ETL → 数仓 → 指标 → 页面。
    与第 10 项（真实连接器）互补：连接器解决"从既有数据源导入"，录入应用解决"随时手动补录"。
    要点：
    - **录入表单由契约派生**（见「仓库结构」的三条约束）：可录入的通道与单位来自
      `semantic_models/*.yml`，避免"格式对、单位错"这一类静默错误从入口漏进来；
    - **ETL 按自然键幂等 upsert**：`(subject_id, observed_at, channel)`，与
      `fact_observation` 的主键一致；迟到数据与重算范围的处理与第 9 项（增量/watermark）共用一套逻辑；
    - **业务库不要并入数仓**：OLTP 负责可变录入，数仓仍保持追加 + SCD2 的派生语义。

## v1.0（半年后）

14. **契约 schema 冻结**，并与 Open Semantic Interchange / Apache Ossie 对齐（做适配器，不另立格式）。
    **顺带做命名统一**：`date.weekday` 实际映射到 `dim_date.weekday_name`，理想命名是
    `date.weekday_name`。这是 **breaking change**，留到与 Ossie 命名对齐时一并处理，避免改两次。
15. **第二个 adapter**：把执行层从"个人主体"抽象出来，验证它不是一次性项目。
    候选：教育场景（用户已有经验，但注意不要用公司数据）、公开健康数据集、家庭设备遥测。
    **前置条件：v0.2 第 5 项（领域描述符）必须已完成**。

## 明确不做

- 看板拖拽编辑器（BI 已过剩，且会稀释"执行层"定位）
- 多租户与云端托管（v1.0 前不做；`local-first` 是定位的一部分）
- 自研 SQL 引擎（用 sqlglot，把精力放在强制校验上）
- 语义格式标准（已被 Apache Ossie 占据，只做适配）
- benchmark 刷榜（基准本身不可信）
